5.1. Configuration des logs

Les fichiers de logs sont primordiaux pour analyser a posteriori un comportement non souhaité de l’application.
L’équipe en charge de la maintenance du produit Arcade GED vous demandera de les fournir dans le but d’identifier plus aisément la source du dysfonctionnement relevé.

5.1.1. Configuration générale

La librairie utilisée pour "écrire" les logs est logback

Le fichier xml/DOSSIER_logback.xml contient la définition globale des logs.

Ce fichier est écrasé / ré-écrit à chaque démarrage de l’application

Le fichier WEB-INF/classes/logback.properties est utilisé pour personnaliser les niveaux de logs.

Concernant la définition des logs, c’est le seul fichier devant être modifié.

Pas défaut, les fichiers de logs seront générés dans le répertoire ./logs de l’application.
Ce répertoire peut également être modifié via la clé log_path, définie dans ce même fichier de configuration.

Nul besoin de redémarrer l’application pour que les modifications soient appliquées, le fichier logback.properties est scruté pour tout changement, avec un délai maximum de 1 minute.

Les différents niveaux de logs possibles sont :

Niveau Description

TRACE

Niveau le plus détaillé, utilisé pour le suivi du programme pas à pas

DEBUG

Informations utiles pour le débogage

INFO

Messages informatifs indiquant le bon déroulement de l’application

WARN

Signale un problème potentiel, mais qui n’empêche pas l’application de fonctionner

ERROR

Indique une erreur qui affecte le fonctionnement de l’application

OFF

Désactive complètement la journalisation
Exemple de fichier logback.properties
# This file defines logback properties
log_path=${dossier_app}/logs
#main log level
log_level=INFO
log_level_digitech=INFO
log_level_dossier=INFO
log_level_viewer=ERROR

5.3. Autres données d’exploitation

Afin d’optimiser ce fonctionnement, notamment dans ces échanges avec la base de données et le serveur Airs, {arcadegd} met en cache de nombreuses données.

Ces caches peuvent être de type :

  1. mémoire: ces données mises en cache permettent d’éviter des appels vers le serveur Airs. ces caches ont pour propriétés d’être :

    • limités en taille (nombre d’éléments dans le cache). En cas de dépassement, les éléments les plus anciens sont supprimés du cache avant ajout des nouveaux éléments.

    • initialisés au démarrage de l’application pour les données de paramétrage.

    • remplis au fil de l’eau pour les données contextuelles (résultats de recherche, derniers documents consultés, …​)

  2. fichiers: ces caches permettent également d’éviter :

    • de trop nombreux échanges avec le serveur de stockage de fichiers,

    • des conversions incessantes d’un format de fichier vers un autre (ex : doc vers pdf, pdf vers png, …​)

6.1.2. Personnalisation des couleurs

Les fichiers css de l’application ne doivent pas être modifiés, dans aucun cas.
En effet, lorsqu’un patch (correctif ou évolutif) est appliqué, ces fichiers seront écrasés.

Seuls les fichiers présents dans le répertoire custom permettent une personnalisation de l’application au niveau UI/look.

La personnalisation des couleurs principales est (plutôt) rapide.
Elle consiste seulement en redéfinissant certaines clés css dans le fichier custom/ui/css/custom.css.

Ce fichier est systématiquement inclus dans la page et permet donc de surcharger les propriétés ciblées/souhaitées.

Les clés principales (jeu de couleurs) sont :

  • --theme-main-color : couleur principale

  • --theme-main-bg-darker-color : couleur plus foncée, relativement à la couleur principale, utilisée notamment comme couleur de fond de certains composants.

  • --theme-main-bg-brighter-color : idem ci-dessus, mais en teinte plus fade/claire comparativement à la couleur principale

  • --theme-main-brighter-color : couleur plus claire comparativement à la couleur principale

  • --theme-main-color-fade : idem, peut être identique à la couleur précédente.

Concernant les icônes, la plupart peuvent avoir leur couleur automatiquement mise à la couleur principale.
Celle-ci est appliquée via un attribut css filter sur tous les icônes marqués avec le styleClass iconTheme.

Pour générer ce filter, veuillez vous rendre sur un générateur html telle celui-ci et copiez le résultat dans la variable --icon-theme-filter.

Pour un code couleur de ce type

voici les paramètres css associés (via le fichier custom/ui/css/custom.css.)

.bg-orange {

6.5. [Cron] ajout d’une tâche planifiée

6.5.1. Introduction

Certaines actions sur la base documentaire n’ont pas besoin d’être exécutées immédiatement,
notamment parce que ces opérations peuvent lourdes, coûteuses (conversion de documents, push ou export vers un système externe).

C’est entre autres pour ces cas-là que des tâches planifiées peuvent être exécutées à fréquence régulière pour effectuer les actions souhaitées.

Le module adminAIRS permet de configurer ces tâches facilement.

6.5.2. Déclaration

Ces tâches planifiées consistent en :

  • la définition d’un script {groovy} de type Task

<Script id="BK_INTEGRATION">
  <script>BK/Task/BK_Integration.groovy</script>
  <type>Task</type>
</Script>

Veuillez svp vous référer à la documentation dédiée aux scripts {groovy} pour obtenir une description des paramètres et quelques exemples.

  • la définition d’un intervalle/fréquence d’exécution (attribut planning)

<task code="BK_TASK_INTEGRATION" scriptId="BK_INTEGRATION" flowCodes="BK"  executeBehavior="SCHEDULED" asynchronous="true" title="Traitement des documents à
intégrer" description="Traitement des documents à intégrer, est exécuté toutes les minutes" enabled="true" startDate="2014-01-01T12:00:00.000+01:00" planning="0 0/1 * * * ?">
</task>

L’attribut planning n’est pas un classique/exact cron (unix) mais quartz.
La documentation indiquée ci-dessus est suffisamment explicite. Cependant, n’hésitez pas à utiliser votre agent IA préféré, qui excellera probablement dans la définition du cron souhaité.

Quelques exemples :

  • toutes les 2 minutes : 0 0/2 * ? * * *

  • toutes les 5 minutes, les lundis, mercredis et vendredis seulement : 0 0/5 * ? * MON,WED,FRI *

  • à 6h et 21h les jours ouvrés : 0 0 6,21 ? * MON-FRI * 

6.6. [Redirect] Définitions des URLs de redirection

6.6.1. Introduction

Il peut être utile d’accéder directement à l’application Arcade GED dans un contexte précis :

  • Accès direct à un résultat de recherche

  • Accès direct à un document

  • …​

Ces accès externes sont fréquemment utilisés, notamment dans les cas suivants :

  • hyperlien défini dans un mail

  • redirection/hyperlien défini à partir d’une autre application métier

Lors de la redirection, si l’utilisateur n’est pas connecté, celui-ci sera d’abord redirigé vers l’écran de login/connexion.

Si le SSO est activé, l’opération d’authentification sera alors transparente pour l’utilisateur.

6.6.2. Définition

L’idée est simplement de définir et appeler l’URL de redirection avec les paramètres adéquats.

L’URL de redirection est construite ainsi :
http(s)://<hostname>:<port>/<context>/faces/redirect.jspx?outcome=XXX&param1=value1&param2=value2

avec les paramètres suivants :

Code Description Valeurs possibles/Remarques

outcome

page cible attendue suite à l’appel

  • gotoSimpleView : résultats de recherche

  • gotoThreeViews : résultats de recherche, vue 3-fenêtres

  • search/gotoSearch : recherche

  • searchAdvanced/gotoSearchAdvanced : recherche avancée

  • gotoDocumentUnitaire/gotoUnitView : Vue document

  • gotoTreeView : Vue arborescente

  • documentViewer : Vue Pièce jointe)

docId

Identifiant du document dont l’affichage est souhaité

Obligatoire si outcome est parmi (gotoDocumentUnitaire, gotoSimpleView, documentViewer, gotoTreeView)

attId

Identifiant de la pièce jointe dont l’affichage est souhaité

L’attribut docId doit également être renseigné dans ce cas

cty

Content-type cible lors d’une recherche

orgId

ID de l’organisation sur laquelle basculer

optionnel

Recherche

query

Requête AIRS complète

ex : D_CREAT = "01/01/2026" OU STATUS="New"

Critères de recherche séparés

La définition s’effectue alors pour 10 critères maximum fieldX=<CODE>&opeX=<OPE>&valueX=<VALUE>

X étant l’index sur l’intervalle [1,10]

field

Code du champ AIRS

ope

Opérateur de recherche sur ce critère

  • equal : valeur égale à

  • greater : valeur supérieure à

  • less : valeur inférieure à

  • between : valeur comprise entre

  • notBetween : valeur non comprise entre

  • in : valeur parmi les éléments définis (séparés par ,, exemple value1=8479;9999)

  • notInt : valeur non présents dans les éléments définis

  • isNotNull : valeur non nulle (l’attribut valueX n’est alors pas nécessaire)

  • isNull : valeur nulle (l’attribut valueX n’est alors pas nécessaire)

value

Valeur du critère recherché

opLoc

Opérateur de jonction

Optionnel.

  • ET : Les éléments recherchés doivent répondre à tous les critères spécifiés (valeur par défaut)

  • OU : Les éléments recherchés doivent répondre à l’un des critères spécifiés

Les attributs/critères transmis dans l’URL doivent être encodés !
Exemples
http(s)://<hostname>:<port>/<context>/faces/redirect.jspx?outcome=gotoSimpleView&cty=CR&query=D_CREAT<"01/01/2025"

http(s)://<hostname>:<port>/<context>/faces/redirect.jspx?outcome=gotoSimpleView&cty=CR&field1=D_CREAT&ope1=less&value1=01/01/2025
